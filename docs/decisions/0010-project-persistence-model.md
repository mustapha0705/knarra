# 0010: Project Persistence Model

- Status: Accepted
- Date: 2026-11-17

## Context

M4 stores projects in PostgreSQL. Several things had to be decided before a schema could exist: what one saved project consists of, how two editors are kept from overwriting each other, what a version is and when it may be created, how assets are recorded before uploads exist (M5), and how the persistence code is tested when a PostgreSQL server and its credentials are not always available to the test run.

This ADR was written during unattended overnight work and records decisions taken under delegated discretion. It should be reviewed as a proposal as much as a record.

## Decision

1. **A project row holds two separate documents.** `composition` is the validated render model. `editor_state` is Canvas and other editor-only state. They are separate columns so that the renderer can never read Canvas state (ADR 0001, invariant 1).
2. **Optimistic concurrency by numeric revision.** Every project has an integer `revision`. A save must state the revision it was based on, and the write is a single `UPDATE ... WHERE id = $1 AND revision = $2`. A save based on an older revision is refused with the current revision and writes nothing. There is no locking and no merging.
3. **A working save checks structure only.** The Composition must parse (`parseComposition`), but it need not be renderable. A project being edited can have an empty timeline or a clip that is not yet valid, and must still be saveable.
4. **A version is an explicit, immutable, renderable snapshot.** Creating a version copies the Composition, the editor state, and the asset catalog into `project_versions`. It is refused unless `validateComposition` passes. A database trigger rejects every `UPDATE` of a version, and the API offers no route that changes or deletes one. Deleting a whole project removes its versions.
5. **Render jobs reference a version.** `render_jobs.project_version_id` is `NOT NULL` with a foreign key, so a job cannot exist without an immutable version (ADR 0003). M6 defines the job lifecycle.
6. **Assets are recorded per project with a `verified` flag.** Until M5 the only source of asset metadata is the browser, so assets are saved with `verified = false`. The client cannot set the flag. From M5 the server sets it after probing the stored file. Unverified metadata must not be trusted for rendering; KNAR-302 already probes files itself for that reason.
7. **IDs.** Project and version IDs are generated by the server. All IDs are text in the kernel ID format, enforced in the application and by `CHECK` constraints.
8. **Migrations are plain SQL files**, applied in name order, once, each in a transaction with the row that records it. The server applies pending migrations at start, and `npm run migrate` does the same on demand. If the database contains a migration the code does not know, startup is refused instead of guessing.
9. **The database is optional at startup.** Without `DATABASE_URL`, or if the connection fails, the server starts and `/api/projects` answers 503. Export does not need the database yet.
10. **Tests run on an embedded PostgreSQL (PGlite).** The repository depends on a narrow `Database` interface. In tests it is backed by PGlite, a PostgreSQL engine running inside the test process, so the real SQL and migrations run with no server and no credentials. Setting `TEST_DATABASE_URL` runs the same tests against a real server as well. PGlite is a development dependency only; production code never imports it.

## Consequences

- A stale save is a visible conflict, not a silent overwrite. The frontend must handle 409 by reloading (KNAR-402).
- "Save" and "can render" are different questions with different answers, and the UI can say which one failed.
- Version rows duplicate the Composition and editor state. That is the cost of immutability; media itself is never copied (invariant 9).
- PGlite and a PostgreSQL server can differ. The `pg` adapter is small, but it is only exercised when `TEST_DATABASE_URL` is set. It was not exercised when this was written, because no server credentials were available.
- PGlite runs one connection, so its "concurrent" saves are serialized. The single-statement conditional `UPDATE` is what makes concurrent saves safe on a real server; that property follows from PostgreSQL's row locking and should be confirmed with `TEST_DATABASE_URL`.
- There is no authentication or ownership yet: every project is visible to every caller. Acceptable only for local development, like the open CORS noted for M6.
- `editor_state` is opaque and size-limited. If the frontend embeds media in it (data-URL posters, for example), saves are rejected; KNAR-402 must strip those.
